# Backlog Item: 0005 — Calliope InformationUnit

**Backlog Item ID:** 0005

**Backlog Item Revision:** 000.004

**Standing:** Proposed work specification reconciled with the Solution Architect's adjudicated BL-0005 DR-7 decisions recorded in software HCRL 0.1.0/011 DR-13. Revisions `000.001` to `000.003` remain preserved; implementation and acceptance remain subject to their separately governed assignment and HCRL review.

## Overview

### High-Level Synopsis of Effort

Define and verify the shared Calliope model for a single governed InformationUnit (IU).

### High-Level Synopsis of Activities

Realise the reconciled model in Draft 002.007 §1 using the existing Naming API. Implement model-local construction, validation and lifecycle semantics without taking over persistence, security adjudication or content processing responsibilities.

### High-Level Synopsis of Outcome

Calliope provides a documented IU model with stable identity, initialised metadata, immutable InformationQuality and one governed representation per IU. The model distinguishes clone derivation from minimum-metadata derivation, retains established origin and expected-revision semantics, and supplies separate RAW container and content schema Topics.

### High-Level Synopsis of Acceptance Criteria

Focused tests demonstrate the exact name projection, immutability, revision expectations, authority revisions under the same UUID, Themis-Krites security boundaries, both successor contracts, exact vocabulary paths, separate media types, portable Content and safe handling of invalid input. Existing Naming behaviour passes regression testing.

The branch starts from the accepted standalone Calliope Naming implementation. `Topic` is an immutable value with a qualified, case-sensitive, version-independent identity. `Topic.getName()` joins raw values with periods, omitting qualifiers and entry versions. Reuse the supported Topic builders and accessors. The current IU designation is a string projection and the IU UUID is the sole instance identifier. The assignment requires no legacy compatibility. Consumer work is outside scope, including Store selection, persistence and cache operations, policy enforcement, reference resolution, Summary and search projections, routing, masks, grading and assurance processes, migration, and provider or wire codecs. The model preserves applicable behavioural obligations, including the Summary reference and authoritative revision semantics. ## Expected / Associated Activity

1. **Identity and construction.** Build the IU with immutable `id : UUID` as sole instance identifier, immutable `informationConcept : Topic`, and direct revisionable `description : String`. `informationConcept` replaces `ConceptFDN` and `informationProfile`. Implement `getName()` as `informationConcept.getName() + id.toString()` with no inserted separator. Expose the qualified `informationConcept` as the MI-05 match value. Initialise every defined metadata container with applicable defaults.
2. **InformationMetadata.** Use `PersistenceLifecycleMetadata` (Mnemosyne-established authoritative Managed Revision, disposition and legal hold) and `CacheLifecycleMetadata` (Mneme cache state and Active Generation) as the direct lifecycle allocations. Preserve the distinct revision axes and persistence handshake responsibilities. A local modification retains its originating Managed Revision as the expected revision for a subsequent governed write; Mnemosyne establishes the successor after successful persistence. In `OriginMetadata`, permit initially unknown source system Topic, first Harmonia entry component Topic and entry `Instant`, including for internally generated information. Permit population of unknown values and protect established values against change, including Topic entry versions; a Topic re-statement is idempotent only when its versioned canonical form is identical. Keep `PersistenceGateway`, `GatewayEndpoint`, `InformationLocation` and `InformationOwner` immutable per governed revision. An authorised relocation, ownership change or information-authority change establishes a new revision under the same UUID while preserving the previous snapshot and expected Managed Revision. `informationAuthority : Topic` is required on `InformationMetadata`. `SecurityMetadata` is immutable; Themis-Krites adjudicates strengthening, weakening and replacement. Calliope does not decide security policy, and this work does not implement a Krites service. Routing and itinerary belong to Pragma/Pragmatosis.
3. **Relationships.** Use `InformationMetadata.Relationships.relationships : List<InformationUnitRelationship>` for internal and external semantic links. Each element has `type : RelationshipType`, `role : RelationshipRole` and `target : URI` using the values in Draft §1.4. Support URN-based persistent identities and their string representation. An `INTERNAL_IU` target identifies the IU by UUID. Preserve applicable local and remote validation responsibilities. Keep these semantic links separate from the locator for externally persisted Content. [Draft §1][draft]
4. **InformationQuality.** Add the distinct IU constituent containing required, non-blank `owner : String`, `grade : {Anecdotal, Informational, Canonical}` and `certifications : Map<String, String>` (certifier to certification). The owner identifies the party responsible for the quality assessment, distinct from revisionable `InformationOwner`. Preserve grades assigned according to origin and assurance under the Integration Architect's release criteria. Protect all InformationQuality properties for the IU's lifetime. Subsequent validation yields a new IU with provenance through the owning process. `Canonical` is a quality grade independent of authoritative standing under [AX-06][ax06].
5. **InformationRepresentation.** Compose one governed representation per IU. A transformation producing a new representation requires a new IU with provenance, including for equivalent representations. Governed revisions preserve representation. Include `ContainerMetadata` with `containerConcept`, `containerSchema` and required `containerMediaType`, and `ContentMetadata` with required `contentConcept`, `contentSchema`, `contentMediaType` and an initialised `ContentDetail`. Media types are IANA identifiers stored separately from concepts and schemas; do not make media types content-concept values. `contentConcept` describes what the Content represents. `contentSchema` identifies its structure, schema or profile and carries applicable Topic entry versions. When no distinct content schema is specified, use the separate RAW ContentSchema path `Domain=ICT.Owner=fhirfactory.Standard=harmonia.Concept=InformationUnit.ContentSchema=RAW`; retain the RAW container path `Domain=ICT.Owner=fhirfactory.Standard=harmonia.Concept=InformationUnit.InformationContainer=RAW` separately. Generic profiles use the defining organisation and standard's own `Domain → Owner → Standard` path, preserve standard-defined intermediate containment and append `Profile[:version]=<name>` without an implied relationship to an underlying resource. `InformationVocabulary.profileSchema` may apply its documented base restrictions, but they do not constrain generic Topic construction or other valid standard-defined hierarchies. Do not restore the obsolete Harmonia data-schema path. Keep format and encoding distinct from the schema and preserve the native payload instance version independently. FHIR R4 resource schemas use `Domain=Health.Owner=HealthLevelSevenInternational.Standard=FHIR.Release:4.0.1=R4.Resource=<resource-name>`; `R4` is the release designation and `4.0.1` its specific version, with no independent resource-definition versions. Preserve the common `Domain → Owner → Standard` hierarchy and use standard-defined subordinate containment rather than a separate relationship model.
6. **Content and integrity.** Model `Content.reference` as the locator for externally persisted Content and `Content.data` as inline portable Content. Require exactly one. Encode inline text as UTF-8 and require supplied references to be absolute URIs. An inline IU can be constructed before a persistence reference exists. Mneme, Mnemosyne and the PersistenceService own provider-reference generation and association management under the governed interaction contracts. Later persistence can establish a locator while preserving the IU's governed information representation. Summary projects the existing locator from the single authoritative association and leaves it absent when none exists. `ContentDetail` carries provider-supplied byte `size`, `checksum` and `checksumAlgorithm`, plus applicable `language`, `height`, `width`, `frames`, `duration` and `pages`. Validate non-negative size and duration, positive supplied dimensions/frame/page counts, and the existing BCP-47-shaped language syntax. A checksum and algorithm must be supplied together and are never silently defaulted. The PersistenceService determines how and when to verify integrity. Preserve the existing durability guarantees and reference-only Summary registration boundary.
7. **Successor derivation.** Provide `deriveSuccessorAsClone(newId, role)` to create a complete clone with a new UUID, copied data and associated metadata, all existing relationships plus source provenance, and fresh persistence/cache lifecycle metadata. Provide `deriveSuccessorWithMinimumMetadata(newId, role)` to create a new UUID while inheriting only `OriginMetadata` and `SecurityMetadata`, adding only source provenance, and reinitialising lifecycle metadata. Its caller-confined builder requires a new concept, description, quality, authority and representation; coordinates default to unplaced and may be supplied. The builder does not allow inherited origin, security or provenance to be replaced. Both operations preserve the source snapshot and its governing authority boundaries.
8. **Keep the Java model cohesive and format-neutral.** Use `net.fhirfactory.harmonia.model.core.information.entity` as the package reference. Treat owned metadata and representation structures as dependent values. Leave unspecified Java types, builder signatures, class decomposition and applicable media detail validation to detailed design within the agreed contracts. Document invariants, mutation boundaries and failure behaviour. Protect mutable buffers and collections and keep sensitive values out of diagnostics. [Initial Model Architecture][package] · [Object and Class Granularity][granularity] · [Immutability Guidelines][immutability] · [Serialization and Format Selection][serialization] · [Implementation Guide][guide]

## Acceptance Criteria

| Criterion | Observable result | Verification / expected evidence |
| --- | --- | --- |
| AC-1 — Identity and name | The UUID is the sole instance identifier. `getName()` concatenates the raw Topic name and UUID with no separator. The qualified `informationConcept` remains available for MI-05, and description is revisionable without mutating an earlier snapshot. | Test exact output using an explicit UUID and Topics with qualifiers and optional entry versions. Verify stable identity across revisions, description snapshot preservation, and that supported TopicMasks evaluate the qualified concept through the existing Naming API. |
| AC-2 — Metadata, relationships and security | Containers are initialised. Local updates preserve the origin Managed Revision as the expected write revision; Mnemosyne establishes its successor after successful persistence. Required information authority changes through a new same-UUID snapshot. Established origin Topics cannot be re-versioned. Themis-Krites adjudicates security proposals; Calliope does not decide policy. | Test initial defaults, origin establishment and rejected replacement/version changes, separate Managed Revision and Active Generation, coordinate/authority snapshot preservation and expected-revision retention. Exercise every relationship type and role, URI string round trips including a URN, UUID-based `INTERNAL_IU` targets, and immutable security proposals without Calliope policy decisions. |
| AC-3 — Governed revisions and successor derivation | Coordinate or authority changes create a new governed revision under the same UUID, preserve prior snapshots and retain the originating Managed Revision. Clone derivation creates a complete new IU, retaining existing relationships and adding provenance. Minimum-metadata derivation inherits only origin and security, supplies provenance only and requires the caller's remaining data. | Verify coordinate and authority revisions preserve snapshots, identity, representation and expected revision. Test clone field/metadata copying and lifecycle reset; test minimum-metadata input validation, inheritance exclusions, provenance-only relationships, optional coordinates and lifecycle reset. Verify both operations require a distinct UUID and that a failed builder can be corrected and retried. |
| AC-4 — Representation, schemas, media types and references | `contentConcept` and `contentSchema` remain mandatory. The RAW content schema and RAW container schema are separate qualified Topics. Schema structure and versions remain independent of IANA media types, encoding and native payload version. Exactly one Content carrier is present. | Test the exact RAW paths, mandatory concept/schema inputs, all 146 FHIR R4 resource Topic paths, generic profiles under their governing organisation and standard, standard-defined intermediate entries and version semantics. Test media type normalization and invalid cases, inline text and binary construction, absolute references, both/neither carrier rejection, UTF-8, byte fidelity and defensive copying, ContentDetail validation, and provider integrity metadata. |
| AC-5 — Isolation and evidence | Calliope remains a standalone model library. Invalid operations reject safely and preserve valid state. | Run `mvn -B -ntp -pl calliope -am test` for IU unit tests and Naming regression; run applicable solution-wide verification and `jdeps`. Review dependencies, public APIs and documentation for boundary conformance. The ArchUnit/Paradeigma requirement is retained, not retired, but execution is deferred until Harmonia begins implementing complete subsystems; the current JUnit, Maven verification and `jdeps` evidence is sufficient for BL-0005 as recorded in [HCRL DR-5][hcrl-dr5]. For a later software candidate, record applicable solution-wide regression, integration and conformance results under the [Software Development Praxis][verification]. |
| AC-6 — InformationQuality | `InformationQuality` is a distinct lifetime-immutable IU constituent with a required, non-blank, lifetime-immutable assessment owner. Its assessment owner is separate from coordinate ownership, and `Canonical` is independent of authoritative standing. Subsequent validation has a distinct IU UUID and source provenance. | Exercise all three grades, invalid owner inputs, and attempts to mutate the certification map at input or through a returned value. Verify quality stability across a coordinate-owner revision, keep grade independent of authority in the fixtures, and verify distinct identity and source provenance for subsequent validation. |
