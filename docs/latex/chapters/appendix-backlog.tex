\chapter{Architecture and Implementation Backlog}
\label{app:backlog}

This appendix records identified work required to converge the Harmonia implementation toward the target architecture. Unlike the Architecture Requirements catalogue, backlog items are intentionally implementation-aware and may be completed, replaced, decomposed, or retired as the codebase evolves.

\section{Backlog Conventions}

Backlog identifiers use the form \texttt{BL-<DOMAIN>-nnn}. Each item should identify the requirement(s) it supports and, where relevant, the architecture finding that caused the work to be raised.

Suggested lifecycle states are \texttt{IDENTIFIED}, \texttt{PLANNED}, \texttt{IN-PROGRESS}, \texttt{BLOCKED}, \texttt{DONE}, and \texttt{SUPERSEDED}.

\section{Architecture Technical Debt}
\subsection{Execution Context and Context Propagation}
\subsubsection{BL-ARCH-01 --- Replace ThreadLocal CORS Context in OperationsServerManager}
\paragraph{Description}
Review and refactor OperationsServerManager so the validated CORS origin is propagated explicitly as request scoped state rather than through CURRENT\_ALLOWED\_ORIGIN ThreadLocal..
\paragraph{Priority} 
Low.
\paragraph{Driver} 
Maintainability and future concurrency safety.
\paragraph{Rationale} 
The current implementation is safe because the value is established and cleared within a finally block. However, correctness depends on the server's current thread-per-request execution model. Explicit request-context propagation would remove that coupling and make future asynchronous/executor-based processing safer.
\paragraph{Acceptance Criteria} 
No CORS/security state stored in ThreadLocal; validated origin travels explicitly with request/response processing; existing trusted/untrusted/no-origin/preflight behaviour unchanged; existing CORS tests remain green; no changes to authentication or Themis authorization semantics.
\paragraph{Supports} 

\paragraph{Related} 
CORS Hardenning (see xxxx).

\section{Harmonia - Audit}
\subsection{BL-AUDIT-01 — Introduce a typed Harmonia Security Domain}

Replace the current string-based securityDomain representation ("CLINICAL", "AUDIT", "OPERATIONS", "PROVIDER_REGISTRY", etc.) with a canonical typed Harmonia/Themis security-domain value or enum, and propagate it consistently through ThemisSecurityContext, ThemisResource, ThemisAuditEvent, policies and related contracts.

\paragraph{Rationale:} Task 06 correctly retained String securityDomain because the repository currently only has string constants and changing this would expand Step 01 substantially. The exploration explicitly identified this as the smallest compatible choice.

\paragrahp{Timing:} Foundations cleanup after Tasks 06–10, unless another task creates a natural migration point.

\subsection{BL-AUDIT-02 — Relocate immutable audit evidence to dedicated Operations/Audit persistence} 
Logical ownership is AUDIT/operations rather than clinical; defer physical movement so Task 06 doesn't turn into the persistence redesign covered by later tasks.

\subsection{BL-AUDIT-03 — Database-level audit immutability hardening}
 Consider PostgreSQL permissions/triggers or equivalent append-only/WORM controls after the application/persistence architecture settles. This adds defence-in-depth beneath the service and persistence invariants.

\section{Backlog Sequencing}

The current preferred sequence is:

\begin{enumerate}
    \item complete Security convergence;
    \item complete Provenance and immutable Audit convergence;
    \item complete persistence/search/recovery convergence;
    \item complete validation/governance and Ponos/Erga processing foundations;
    \item preserve and verify Petasos/runtime convergence;
    \item commence the Clinical/LHR backlog (\texttt{BL-CLIN-001} onward);
    \item implement Iris-Clinical against the stable Clinical FHIR service;
    \item introduce selective clinical authoring only after terminology and governance prerequisites exist.
\end{enumerate}

Large capability backlog items, particularly \texttt{BL-CLIN-002} and \texttt{BL-CLIN-003}, should remain capability-sized until their prerequisite foundations converge. They can then be decomposed into bounded Junie-sized implementation work packages.
