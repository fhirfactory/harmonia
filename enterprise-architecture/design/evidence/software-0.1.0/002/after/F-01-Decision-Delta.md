# F-01 decision delta — Final.001 to Draft.002

**Scope** · Comparison of the historical design and the accepted discussion decisions consolidated for review in Draft.002. This is review evidence for the proposed design transition.

[Final.001][final] supplies the historical comparison. The [F-01 adjudication record][f01] controls the Draft.002 column, including corrections to API ownership, generated values and the version model. Cross-source conflicts are recorded in the [architecture reconciliation](F-01-Architecture-Reconciliation.md).

| Subject and decision IDs | Final.001 | Accepted F-01 decision incorporated in Draft.002 |
| --- | --- | --- |
| Topic identity, equality and hashing · F-01.1 | `TopicID` is a full UUID. Substantive replacement has a different UUID. `Topic.name` has an applicable-registry uniqueness rule. | Non-versioned canonical name is identity and the basis for equality and hashing. Version-sensitive comparison is separate. Applicable registry/reference treatment remains an architecture question. [Draft §1][topic] |
| Immutability · F-01.2 | Topic definition, containment and names are immutable. | Topic and its entries are strictly immutable, with defensive copying, deterministic names and new objects for changes. [Draft §1][topic] |
| Sequencing and repeated qualifiers · F-01.3–F-01.4 | Explicit sequence keys persist and travel in exchange. Reject gaps, duplicates and ambiguous order. | Deterministic order is meaningful. Keys are implementation details. Repeated qualifiers are valid at distinct positions. [Draft §1][topic] |
| Hierarchy and structural containment · F-01.5–F-01.6 | Root-to-leaf qualified entries and exact/inclusive discrimination. | Implicit hierarchy of whole entries. Literal ancestry and equality are distinct from mask prefix matching. [Draft §3][hierarchy] |
| Position, bases and field matching · F-01.7–F-01.8, F-01.10 | Two exclusive bases, `TopicNameBased` and `TopicCanonicalNameBased`. Both are positional, with qualifier and value tested separately in canonical mode. No version regex. | One ordered field-expression model. Qualifier and value are independent and each position can constrain version. An omitted constraint accepts an absent version. A supplied constraint, including `.*`, requires a present version that matches the regex. Only trailing candidate entries can be admitted. [Draft §4][mask] |
| Construction and literal helpers · F-01.9, F-01.19 | No corresponding entry factories or fluent literal/regex distinction. | Immutable convenience factories and fluent builder for qualifier, value, optional version and containment, with literal input quoted for RE2/J. [Draft §4][mask] · [§8][api] |
| Mask identity · F-01.11 | Independent stable UUID; changing the definition creates a different UUID. | Structural equality and hashing by ordered original qualifier/value/version expressions and containment. Immutability retained. [Draft §4][mask] |
| API ownership · F-01.12 | TopicMask is a discriminator; no final Java method direction is prescribed. | `TopicMask.matches(Topic)`, the corrected Option A. Topic has no mask-evaluation responsibility. [Draft §4][mask] |
| Full-field matching and compilation · F-01.13–F-01.14 | Regex per element; formal anchoring and invalid-expression treatment deferred. | Full-field matching, construction-time rejection and compilation, retained original expressions and per-call matchers. [Draft §4][mask] |
| Logical interchange · F-01.15–F-01.16 | Explicit sequence numbers in storage and exchange. Precise encoding and wire format deferred. | Exact ordered Topic data and regex expressions, version information and containment survive reconstruction. Compiled patterns are rebuilt. Format and adapters are separate from the core contract. [Draft §5][serialization] |
| Containment and universal match · F-01.17 | Exact/Inclusive enum model, with an unrestricted default. Root encoding deferred. | `includeContainedElements` defaults false. Empty masks are invalid. `TopicMask.all()` explicitly requests a universal mask. Encoding remains qualified. [Draft §4][mask] · [§9][open] |
| RegEx engine · F-01.18 | Formal dialect and repeatable cross-runtime semantics require later evidence. | RE2/J with documented dialect and no automatic Java regex fallback. Resource limits and the RE2/J controls still require evidence. [Draft §4][mask] · [§5][serialization] |
| Null and case · F-01.20–F-01.21 | No explicit null-candidate or case-sensitivity rule in the design. Unrestricted intent excludes accidental wildcard semantics. | All masks return false for null. Topic identity and default regex matching are case-sensitive, with explicit regex flags supported. [Draft §1][topic] · [§4][mask] |
| TopicEntry versions · F-01.22–F-01.23 | Explicitly excludes Topic versioning and a mask version regex; retains distinct IU version concepts. | Each entry may hold an optional String. Null and empty normalize to absent. Nonempty content is preserved and appears in the versioned canonical name only. [Draft §1][topic] · [§2][names] |
| Generated element · F-01.24 | Generate a missing qualifier according to the sequence position. | Generate the missing or empty **value** at assembly. Treat generated `N0`, `N1` and subsequent values like identical literals. Qualifier is required. [Draft §1][topic] |
| Escaping and parsing · F-01.25–F-01.27 | Qualified entries and derived names are described. Reversible text grammar and parsing are deferred. | Canonical escapes for `.`, `=`, `:` and `\`. Strict Topic factories for both projections and a dedicated regex-aware mask parser with explicit containment. The concrete mask grammar proposal is pending review. [Draft §2][names] · [§4][mask] |
| Names and display · F-01.28 and name conventions | Unqualified path, friendly leaf and qualified relative leaf. UUID prefix may be displayed. | Explicit non-versioned and versioned canonical names, existing basic path/leaf projections, and three-entry display as the final two values joined by `-`. `Topic.toString()` returns the versioned canonical name and `TopicMask.toString()` returns the expression. Other display conventions remain qualified. [Draft §2][names] · [§4][mask] |
| Natural ordering · F-01.29 | Sequence keys order entries. No value-level natural-order contract. | `Topic` is comparable by case-sensitive qualifier/value pairs in path order, consistently with equality. `TopicMask` has no natural ordering. [Draft §1][topic] · [§4][mask] |
| Navigation · F-01.30–F-01.32 | Logical containment and sequenced hierarchy, with no corresponding navigation contracts. | Entry-count depth with roots at 1, parent and ancestor prefixes preserving retained versions, and strict literal ancestry ignoring versions. [Draft §3][hierarchy] |
| Resource bounds and short circuit · F-01.33–F-01.36 | Depth is part of matching. No release limits, compile/evaluation safeguard or evaluation order specified. | Release-defined depth and independent field limits, evidenced complexity safeguards where feasible, depth checked first, qualifier/value/version order and first-failure exit. `all()` is explicit. [Draft §4][mask] · [§5][serialization] |
| Diagnostics and logging · F-01.37–F-01.40 | Safe human-readable display helpers and optional short UUID display. No per-match Harmonia logging contract. | Boolean result with safe exit metadata, conditional TRACE and ERROR at the applicable boundaries. Unexpected evaluation failure returns false. Integrate with the Harmonia console and in-JVM satellite paths, retain Themis audit ownership, and verify backpressure and logging failure behaviour. [Draft §6][logging] |
| Concurrency and cache · F-01.41–F-01.42 | Immutable definitions and repeatable matching. No thread or cache contract. | Safe concurrent use with shared compiled patterns and local matchers. No global mask-by-Topic Boolean-result cache. Future result caching requires measured evidence and explicit rationale. [Draft §4][mask] · [§5][serialization] |
| Acceptance evidence and standing · F-01.43–F-01.44 | Repeatable matching evidence and subsequent incorporation reconciliation anticipated. | Mandatory Maven/JUnit behaviour suite and negative cases, preserved Final.001, and Draft.002 pending Solution Architect review. Architecture reconciliation, implementation and release actions remain separately governed. [Draft §9][open] · [§10][acceptance] |
