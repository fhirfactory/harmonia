## A03 — Topic identity and reference migration

**Question** · Under which registry and reference contracts can an existing Topic UUID or historical name resolve to an ordered, typed runtime path without changing its referent or historical meaning?

### Accepted authority and settled design

| Concern | Incorporated contract in 1.1.26 | Settled redesign and remaining alignment |
| --- | --- | --- |
| Identity | Immutable Topic with its own full UUID. Substantive replacement receives a different UUID. The historical reference retains its original meaning. | The reusable datatype has no assigned ID. F-01.1/.76 use the case-sensitive, non-versioned qualified canonical path for value identity, equality and hashing. Independent construction of an equal path yields the same value identity. Amend the historical definition under ADD/HCRL. Preserve an old UUID outside the redesigned `Topic` where an established obligation requires it. F-01.79 preserves architectural element IDs, `canonicalId`, and architecture naming. |
| Order and entries | Explicitly numbered root-to-leaf records of qualifier and name. Storage and exchange retain the sequence numbers. Gaps, duplicates and ambiguous order are rejected. Absent qualifiers normalise by absolute position. | F-01.3/.55–.56/.68–.71/.76 preserve ordered entries. Completed indexed assemblies are contiguous and zero-based. Legacy bindings retain their explicit indices until a binding changes under an approved migration. |
| Names and uniqueness | The unqualified `Topic.name` is unique within the applicable registry. `friendlyName` is the leaf name and `relativeName` is the qualified leaf. The rule establishes neither platform-wide uniqueness nor a registry service or fixed registry partition. | F-01.75 defines raw, qualified and display projections. | Versions | The accepted shape is a qualifier/name pair and has no `Topic.Version`. The accepted mask contract has no version axis. | F-01.22/.25–.29/.52/.75 allow an optional opaque **entry** version. The qualified identity and natural order ignore it. ### Evidence and confirmed discrepancies

- `Topic` requires and exposes a UUID and the Jackson `canonicalName` sequence map. Equality and hashing use the map. A probe confirmed that Topics with equal entries and different UUIDs compare equal. Java equality therefore cannot establish the accepted full TopicID correspondence. The constructor copies the supplied map and checks for gaps. That binding violates the accepted rejection rule. `TopicEntry` trims supplied fields and has no version slot. `toCanonicalString()` concatenates unescaped pairs. ## A04 — IU Topic vocabulary and boundary mappings

**Question** · Which qualifier names and ordered roles form the IU's fully qualified runtime Topic, and which exact representation is read or written at each binding?

### Accepted authority and settled design

The accepted 1.1.26 IU Class has one persistent IU UUID and a historically distinct, immutable IU Topic UUID. Its accepted naming pattern is `harmonia.mneme.iu.<hex-string-of-compressed-uuid>` with deterministic, reversible compression. The baseline calls this the canonical IU Topic name and leaves the exact encoding to the appropriate contract. F-01.75/.78 retain those literal values and their order as the unqualified `getName()` projection in the redesign. The qualified, non-versioned canonical path supplies the derived Topic's value identity. A version-capable canonical form preserves entry data where applicable. The IU UUID remains authoritative for the IU. The namespace and the projection confer no runtime custody or authority. [Topic][topic] · [IU Class][iu] · [IU Final.002 §2][iu-final] · [F-01.75/.78/.79][f004] · [Draft §§3, 7][draft]

### Evidence and confirmed discrepancies

- Current `InformationUnitIdentifier` serializes `uuid` and `topicName`. It emits exactly 32 lowercase hexadecimal digits with no hyphens, retaining leading zeroes by formatting the two 64-bit halves in order. The text parser trims the input, requires the exact lowercase prefix and checks length before parsing the halves. A probe confirmed that a 32-character suffix with a leading plus sign in one half is accepted by the numeric parser, beyond the hexadecimal spelling. The JSON creator compares a supplied name case-insensitively. A second probe confirmed the Topic-object reader accepted the four expected positional values under unrelated qualifiers and with a trailing entry. These are observed input behaviours, with separate compatibility evidence needed for any historical forms proposed for support. Tests cover ordinary, zero, maximum, leading-zero and malformed values. [IU identifier][java-iu-id] · [Identifier tests][test-iu-id]
- `TopicFactory.forInformationUnit` creates `Domain=harmonia.Model=mneme.ModelVersion=iu.DataElement=<hex>` and a fresh Topic UUID on each invocation. `InformationUnitIdentifier.toTopic()` reconstructs it on demand. The four values happen to produce the accepted unqualified spelling. The factory gives `iu` the positional role `ModelVersion` and its string overload only checks for blank before normalizing the supplied suffix. The identifier contains no persistent IU **Topic** UUID, so converting the same IU again cannot preserve that object's UUID as required by the accepted baseline. The positional labels and factory behaviour supply implementation evidence for compatibility only. [TopicFactory][java-factory] · [IU identifier][java-iu-id] · [IU Class][iu]
- The original ConceptFDN/InstanceFDN draft §7.2 used “canonical” for the unqualified text, abbreviated the suffix to `<hex-uuid>` and illustrated a whole-IU `informationProfile`. Its two-field illustration left the accepted baseline's distinct Topic UUID unaccounted for. The original wording is recoverable at Snapshot-004, `6b058c1b332ac6244e6ff2d6aecad9d6c9e2a48d`. Draft §10 defers FDN equality, entry-version participation and serialization for the FDN proposal. Generic Topic equality and versions remain settled by F-01.1/.22/.29. [Original §7.2][fdn-original] · [Draft §10][fdn-deferred] · [F-01 initial decisions][f002] · [F-01.75/.78][f004]

### Solution Architect clarification — InformationUnit identity and ConceptFDN

The revised draft §7.2 records an independently assigned UUID as the IU's durable identity, independent of classification, information representation, ownership, location, lifecycle and version. The IU requires no InstanceFDN. The shared ConceptFDN `solution=harmonia.domain=internal.concept=InformationUnit` describes the IU concept. `InformationRepresentation`, including `ContainerMetadata` and `ContentMetadata`, retains responsibility for describing the payload and its representation. This clarification applies to the draft Design Note. [Operative clarification][a04-task] · [Revised §7.2][fdn]

### Outstanding value-set design and ownership mapping

1. **Base values and extension rules.** For the observed relationship and container families, decide whether to govern a closed base catalogue within open Topic-valued fields, or retain the observed codes as binding-specific compatibility aliases while selecting authoritative values per consuming feature. In either case preserve the open relationship semantics. Decide responsibility for admitting extension values, identity assignment and validation when a feature uses a governed runtime dataset. Separate those duties from native code-system membership and from the Topic registry's identity rules. [IU Final.001 §14][iu-original] · [Models][models] · [DataSets][datasets] · [F-01.79][f004]
2. **Canonical correspondences.** Decide whether the legacy relationship code and Topic forms are supported in particular JSON/reference bindings, along with the treatment of contradictory dual fields and unknown values. Neither choice requires merging container, relationship, security, lifecycle or native classifications. [Relationship model][java-rel] · [IU value sets][java-iu-set] · [G04][groups]
3. **Lifecycle ownership with G06.** Identify the source of truth and allowed projections for each disposition, flag, stage, retention rule and outcome.
