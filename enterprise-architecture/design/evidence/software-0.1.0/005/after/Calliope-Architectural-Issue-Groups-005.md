### G04 — IU representation, reference custody and information authority

**Question and disposition** · Which boundary establishes a coherent by-reference IU/summary, which legacy IU JSON is supported, and where are information-authority assertions represented? DR-3 and DR-9 remain pending. The candidate has one InformationMetadata and one InformationRepresentation with an optional ManagementContext view. The old wrapper has no established production consumer or accepted snapshot corpus in the reviewed evidence. F-01.78 settles the IU Topic projection for the draft and leaves these questions with their original reviews. [HCRL.004][hcrl] · [Carry-forward][carry] · [004 adjudications][decisions004]

**Authority and evidence** · The accepted IU comprises a single representation of ContainerMetadata, ContentMetadata and Content. A Summary omits exactly Content and retains its opaque resolvable reference in ContentMetadata. P2 showed a by-reference Content value can lose its reference in a Summary if ContentMetadata lacks it, and conflicting references can be constructed. This establishes a construction/projection gap. The persisted consequence remains unverified. AX-06 assigns Calliope the semantics of Authoritative, Informational and Anecdotal information independently of persistence and concurrency. P2 found no explicit realization in the model it examined. Existing Content handling distinguishes portable text, binary and references from Java working manifestations, and the tested empty text remains Content. [IU class][iu] · [InformationRepresentation][representation] · [GovernedSummaryWriter][summary] · [AX-06][ax06] · [P2][pass2] · [001 implementation report][report001]

**Proposed disposition and order** · Identify the boundary that validates or supplies the ContentMetadata reference, and require an explicit outcome for missing or contradictory references when creating a governed Summary. Identify authoritative snapshot/wire consumers, then confirm the supported JSON boundary or require bounded replay/migration. Preserve the observed relationship contract of Topic-valued output and legacy string input when evaluating compatibility. Locate how the governed authority concepts are represented in native and metadata contracts before deciding whether any implementation is missing. A mandatory field or new Class requires its own demonstrated need. G02 provides IU reference identity, G06 provides retention and operational ownership, and G05 uses the resulting portable representation and compatibility rules. **Order 3, in parallel with G03.**

### G05 — Workflow payloads, native models and interchange

**Question and disposition** · Which workflow payload behaviours belong to a common model, and which transformations and encodings belong at governed boundaries? DR-3 and DR-4 remain pending. The candidate retains existing Pragma/Ergon FHIR field names and aliases. The shared model already has portable representation constituents, and the workflow-specific mapping requires separate review. [HCRL.004][hcrl] · [P1][pass1] · [P2][pass2]

**Authority and evidence** · AX-02, AX-03 and AX-13 preserve native standards and define the external boundary. AX-14 preserves meaning through translations. NFR-099 prefers XML where practical and permits UI/interoperability exceptions. The IU baseline accepts portable text/binary/reference forms and explicit encodings. P1 and P2 found `ErgonPayload` stores FHIR Task inputs as its general model, classifies ordinary text as JSON, decodes arbitrary bytes as UTF-8 and substitutes stringification after JSON serialization failure. P2 also traced a production ADT caller passing HL7 through a JSON factory. JSON-valued observations raise a separate schema obligation in G06. Annotation choice and MIME text are compatible with the present authority where boundary semantics are preserved. [Axioms][axioms] · [NFR-099][nfr] · [RAD 1.1.25 DR-4][rad4] · [Design Note][design-note] · [P1][pass1] · [P2][pass2]

**Proposed disposition and order** · Establish a neutral workflow payload boundary with explicit content kind, structure, format and encoding, and determine where the existing constituents can be reused. Keep native FHIR Task/HL7 behaviour at its applicable adapter or native representation. Identify the required XML, JSON, binary and reference mappings by consumer/contract, including why each format applies and how invalid input or failed conversion is represented. Preserve published or otherwise supported FHIR shapes unless explicitly migrated. This leaves implementation choices about serializers and Java classes to evidence. Use G01 for trust, G02 for Topic text mappings and G04 for reference and historical format obligations. **Order 4.**
