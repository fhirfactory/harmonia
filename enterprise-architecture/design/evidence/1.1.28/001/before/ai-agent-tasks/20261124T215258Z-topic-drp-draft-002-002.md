## 3. Adopt the agreed version-matching model

### 3.1 Topic version representation

Topic versions remain optional opaque strings.

A version may contain nonnumeric text, provided it satisfies the existing Topic version validation rules.

No parsing, normalisation or numeric interpretation occurs when constructing or storing a Topic.

### 3.2 Supported version constraints

Define the following constraint categories:

| Constraint | Meaning |
|---|---|
| `1.2` | Exact, case-sensitive text comparison |
| `=1.2` | Numeric equality |
| `<1.2` | Numeric less than |
| `<=1.2` | Numeric less than or equal |
| `>1.2` | Numeric greater than |
| `>=1.2` | Numeric greater than or equal |
| `>=1.2,<2.0` | Numeric bounded range |
| Omitted constraint | No version restriction |
| Present-empty constraint | Valid, but never matches |

The existing distinction between omitted and present-empty version constraints must survive construction, equality, hashing, canonical reconstruction and XML interchange.

A constraint that cannot be interpreted according to its declared semantics must never become unrestricted.

### 3.3 Numeric version syntax

Numeric versions consist of dot-separated, nonnegative integer components.

Examples:

- `1`
- `1.2`
- `1.2.3`
- `01.002`
- `0.0.0`

Leading zeroes are permitted.

A numeric component is a nonempty sequence of ASCII decimal digits.

Do not interpret signs, decimal fractions, scientific notation or alphabetic suffixes as numeric version syntax.

Use bounded, overflow-safe comparisons. Do not rely on Java integer conversion that can overflow.

Retain the original version text.

### 3.4 Numeric comparison

Compare numeric components from left to right.

The first unequal component determines ordering.

Treat missing trailing components as zero.

Therefore:

| A | B | Numeric relationship |
|---|---|---|
| `1.2` | `1.2.0` | Equal |
| `1.2.0` | `1.2.0.0` | Equal |
| `01.002` | `1.2` | Equal |
| `1.10` | `1.9` | Greater |
| `1.2.1` | `1.2` | Greater |
| `2` | `2.0.0` | Equal |

Numeric equality does not imply literal string equality.

`1.2` and `1.2.0` remain distinct stored version strings.

### 3.5 Nonnumeric versions

Exact-text constraints may match nonnumeric versions.

Numeric constraints do not match nonnumeric candidate versions.

For example:

| Candidate version | Constraint | Result |
|---|---|---|
| `1.2-beta` | `1.2-beta` | Match |
| `1.2-beta` | `>=1.2` | No match |
| `1.2.0` | `1.2` | No match |
| `1.2.0` | `=1.2` | Match |

No semantic-versioning or prerelease interpretation is introduced.

### 3.6 Absent versions

A candidate without a version:

- Matches an omitted version constraint.
- Does not match an exact-text constraint.
- Does not match a numeric comparison.
- Does not match a numeric range.
- Does not match a present-empty constraint.

An omitted constraint matches both absent and present versions.

Do not interpret missing candidate versions as zero.

### 3.7 Numeric ranges

Support a bounded numeric range expressed as a lower and upper comparison.

Example:

`>=1.2,<2.0`

Both comparisons must succeed.

Support inclusive and exclusive endpoints through `>=`, `>`, `<=` and `<`.

Reject malformed, contradictory or empty ranges during construction.

A range must have one lower bound and one upper bound.

Do not introduce arbitrary Boolean expressions, disjunction, nested ranges or general-purpose expression parsing.

### 3.8 Constraint validation

Validate constraints when constructing or reconstructing a TopicMask.

Invalid constraint expressions must be rejected.

Preserve builder state after rejection.

Ensure that malformed or unsupported expressions never silently become unrestricted.

The version matcher should remain bounded, deterministic and straightforward to implement.

## 4. Canonical representation and XML interchange

Update the existing design to specify how version constraints are represented in:

1. The TopicMask canonical expression.

3. XML encoding and decoding.
4. Public construction and reconstruction APIs.

`qualifierPattern[:versionConstraint]=valuePattern`

Retain the independently agreed canonical escaping rules.

Preserve the distinction between:

- Absent version constraint.
- Present-empty version constraint.
- Exact-text constraint.
- Numeric equality.
- Numeric comparison.
- Numeric range.

**Important:** Do not silently invent an interpretation where syntax is ambiguous.

For example, determine how an exact-text version beginning with `=`, `<` or `>` can be distinguished from a numeric operator.

Likewise, determine whether a comma is ordinary exact text or a range separator.

Propose the smallest unambiguous lexical treatment consistent with the existing canonical and XML design.
