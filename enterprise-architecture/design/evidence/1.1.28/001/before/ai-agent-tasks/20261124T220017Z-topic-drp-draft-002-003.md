## 2. Preserve agreed version-matching semantics

Topic versions remain opaque strings.

TopicMask supports:

| Constraint | Meaning |
|---|---|
| Omitted | Unconstrained |
| Present-empty | Valid, never matches |
| `1.2` | Exact, case-sensitive text |
| `=1.2` | Numeric equality |
| `<1.2` | Numeric less than |
| `<=1.2` | Numeric less than or equal |
| `>1.2` | Numeric greater than |
| `>=1.2` | Numeric greater than or equal |
| `>=1.2,<2.0` | Bounded numeric range |

Preserve:

- Nonnegative dot-separated integer components.
- ASCII decimal digits.
- Permitted leading zeroes.
- Numerically insignificant trailing zero components.
- Overflow-safe comparison without Java numeric conversion.
- Exact-text matching for nonnumeric versions.
- Numeric mismatch for nonnumeric candidate versions.
- Absent candidate versions failing all explicit constraints.
- Distinct absent and present-empty constraints.
- Invalid constraints rejected before publication or builder mutation.

Numeric equality must not imply literal-text equality.

## 3. Adopt the simplified numeric range-validation rule

Replace the range-satisfiability logic in Draft.002.002.

A range is valid when:

1. Both numeric endpoints are syntactically valid.
2. The first comparison is a lower bound (`>` or `>=`).
3. The second comparison is an upper bound (`<` or `<=`).
4. The lower endpoint is numerically less than the upper endpoint; **or**
5. Both endpoints are numerically equal and both comparisons are inclusive.

Reject:

- Malformed endpoints.
- Missing or duplicate bounds.
- Reversed endpoint ordering.
- Numerically equal endpoints where either comparison is exclusive.

Accept correctly ordered, distinct endpoints without attempting to establish whether a representable Topic version exists between them.

### Examples

| Range | Expected result |
|---|---|
| `>=1.2,<2.0` | Valid |
| `>1.2,<2.0` | Valid |
| `>=1.2,<=1.2.0` | Valid — numeric singleton |
| `>1.2,<=1.2.0` | Invalid — equal endpoints with exclusive lower bound |
| `>=1.2,<1.2.0` | Invalid — equal endpoints with exclusive upper bound |
| `>=2.0,<1.2` | Invalid — reversed endpoints |
| `>1.2,<1.2.0` | Invalid — equal endpoints, both exclusive |

### Remove unnecessary complexity

Remove the proposed algorithm that:

- Constructs a shortest equivalent numeric version.
- Extends versions with trailing numeric components.
- Generates witness values.
- Increments decimal components to find representable values.
- Determines whether the interval contains a version representable within the Topic version length limit.

Remove the associated witness-generation resource requirements and verification obligations.

**Do not replace this algorithm with another satisfiability algorithm.**

Range construction validates endpoint syntax, direction and ordering. Matching evaluates the actual candidate version against both bounds.

This is a deliberate architectural simplification.

## 4. Accept the proposed version-constraint lexical syntax

Adopt the lexical rules proposed in Draft.002.002 §5.

After decoding the outer canonical representation:

- A missing constraint is unconstrained.
- A present-empty constraint is valid but never matches.
- An initial `=`, `<` or `>` selects numeric interpretation.
- Recognise `<=` and `>=` before single-character operators.
- Numeric ranges use exactly two comparisons separated by one comma.
- The lower bound appears first and the upper bound second.
- Numeric expressions contain no whitespace.
- Malformed operator-led expressions are rejected; they never fall back to text matching.
- A leading backslash escapes an initial `=`, `<`, `>` or backslash for exact-text matching.
- A comma in an exact-text constraint remains literal.
- Interior and trailing backslashes in exact-text constraints remain literal.

Preserve the original supplied constraint text for structural equality, hashing and interchange.

Do not introduce a general-purpose expression grammar, Boolean operators or additional matching forms.

Ensure the distinction between the raw version-constraint escape and the outer canonical escaping layer is explicitly documented.

## 5. Accept the proposed XML representation

Adopt the successor XML representation proposed in Draft.002.002 §5 for design purposes.

Ordinary mask entries carry:

- `qualifierPattern`
- `valuePattern`
- Optional `versionConstraint`

Preserve the original raw pattern and constraint text using the established UTF-8/Base64 rules.

The absence of `versionConstraint` means unconstrained.

A present element containing zero decoded characters represents a present-empty constraint.

The reader must reconstruct the exact original expression and interpret it only after strict decoding.

Preserve:

- Explicit ordinary/universal mask kind.
- Ordered entries.
- Containment semantics.
- Deterministic writing.
- Strict completed-record reconstruction.
- Rejection of invalid or missing completed qualifiers.
- Strict XML structure, encoding and whitespace validation.
- DTD and external entity restrictions.
- Bounded input and allocation.

Do not expose internal parsed comparison objects through XML.

### Legacy format identification

The successor XML field representation is approved as a design direction.

**Do not infer that legacy regex records can be interpreted as wildcard records.**

Retain explicit format recognition and legacy selector migration as open architectural decisions.

Do not invent a format discriminator or compatibility mechanism without Solution Architect approval.

Preserve bounded scanning and temporary allocations.
