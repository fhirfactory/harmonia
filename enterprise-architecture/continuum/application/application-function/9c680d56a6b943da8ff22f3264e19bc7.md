# Mnemosyne Adapter (Store)

## Architectural content

Mneme's persistence-facing adapter discovers IU-type capabilities registered by Mnemosyne-side Mneme Adapters / Façades, using the existing shared TopicMask primitive: element-wise regex matching against dot-separated canonical-name elements. It establishes eligible instances and selects among them for the request.

The distributed architecture must support (1) high availability and changeover when an instance becomes unavailable, (2) concurrent processing of distinct IU instances of the same registered IU type across multiple Mnemosyne instances, and (3) load balancing across eligible instances. Capability support and current availability are different facts. Identical, overlapping and disjoint registrations are supported; no one-to-one Store/instance mapping is imposed.

Mneme retains concurrency management for each individual IU. Selection of another Mnemosyne instance must reach the same logical authoritative persistence engine for that IU and preserve version/authority/security guarantees. Instance selection does not replace the IU's governed InformationCoordinates. No concurrent authoritative writes across independent engines are permitted.

Mnemosyne reports factual persistence Outcome; Mneme decides its own subsequent response. Mneme may treat Indeterminate as failure of its own operation without changing the reported persistence status. Changeover does not prove a previous in-flight write failed or make blind mutation retry safe. Availability detection, registration expiry, routing, load policy, failover protocol and coordination machinery remain solution-design responsibilities, with no mechanism selected by this incorporation.
