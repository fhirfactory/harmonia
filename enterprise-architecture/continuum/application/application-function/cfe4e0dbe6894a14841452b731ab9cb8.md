# Mneme-Standard-Cache

## Architectural content

Mneme's lightweight distributed active-IU Summary/reference and operational-coordination cache responsibility. The selected machinery is **Infinispan Server accessed through Hot Rod**, with synchronous distribution as a direction qualified by MC-01/02. Authorised components use Mneme governance and Themis; a Hot Rod client grants no raw-cache bypass.

The IU Summary is the projection of the same accepted InformationUnit excluding **exactly InformationRepresentation.Content**. It retains Identity, applicable Metadata (ManagementContext, InformationCoordinates, SecurityContext, LifecycleContext and optional Relationships), ContainerMetadata and ContentMetadata. A Content reference belongs in ContentMetadata and is opaque to Mneme; Mnemosyne/PersistenceService resolve it with InformationCoordinates. ContentReference is illustrative vocabulary, not a prescribed field encoding. Summary projection does not promote transient ManagementContext data to mandatory durable metadata, create a second IU/InformationRepresentation, independent metadata authority or Summary version lineage. Logical separate Content addressability does not require separate physical databases or a particular native transaction.

Normal population/refresh uses GovernedSummaryReader, GovernedSummarySearch or the coherent Summary from a successful full GovernedWriter. Summary CREATE registers external Content; RETIRE adjusts governed visibility. Mneme decides population, refresh, invalidation and eviction; Mnemosyne does not manipulate either cache. Cache residence, replication and active generations establish no authoritative persistence or independent IU. AX-05 failed/degraded convergence creates no valid active generation; untrusted coordination requires authoritative reconciliation.

Received Content is normally persisted once at ingress; IU references then flow through Petasos/Pragma/workflow scaffolding. Reference availability does not assert an exhaustive cache/search or default bulk Content residency. Logs, AuditEvents, Provenance and Search Result Sets are not universal generic cache streams.

### Retained MC-01–MC-07 qualifications

- **MC-01:** Standard-Cache multi-site topology and active/active consistency need evidence; synchronous distribution/cross-site backup is not native linearizability or safe independent-cluster same-key concurrency.
- **MC-02:** Owner count/site placement, majority/partition/failover and continued governed work after one site loss remain unproved; Mneme retains state-transition concurrency obligations beyond cache operations.
- **MC-03:** Per-JVM memory bounds, safe eviction/lifetime relative to context load/unload/checkpoint and security isolation remain solution/deployment policy under existing Ergon semantics.
- **MC-04:** Durable propagation does not prove immediate replica read visibility. Exact-version/currentness, read-after-write and wait/fail/Indeterminate behaviour use Mneme–Mnemosyne and PersistenceService contracts; no cache affinity mechanism is invented.
- **MC-05:** Active/active N+1 (N > 0) is an architectural target, not a verified product guarantee. With only two physical sites, loss of one prevents **new multi-site durable write Success** without another eligible durable site or explicit owning NFR/persistence disposition. Never weaken Success or claim unqualified N+1 write continuity. Three-plus sites alone do not prove quorum/failover correctness.
- **MC-06:** Five-service reconciliation is deterministically incorporated: historical GovernedSearch identity is reused as sole GovernedSummarySearch, Summary Reader/Writer added, full Reader/Writer retained; no independent Summary IU or sixth method.
- **MC-07:** Existing capability/Feature contributions are reused. Physical remote-client/embedded ownership, observation, deployment and as-built integration remain downstream; no new module or implementation framework is selected.
