# TopicMask

## Architectural content

TopicMask is Harmonia's shared logical discrimination structure, comprising
regular-expression patterns applied **separately to corresponding individual
canonical-name elements** of a Topic. Applicable element expressions must match
under governed syntax/anchoring rules. It is neither one whole-name regex nor a
precomputed enumeration/set of TopicIDs. An element wildcard cannot silently span
adjacent dot-separated name elements. Matching can include subsequently introduced
Topics whose canonical-name elements satisfy the pattern without editing a list.

For example, `<BusinessDomain>.<StandardsBodyName>.InformationCompartment.<CompartmentName>`
illustrates a Topic hierarchy. `*.*.InformationCompartment.PersonalInformation*`
is illustrative shorthand only: an unconstrained element might use `.*` in actual
element-wise regex. Precise anchoring, escaping, missing/excess elements, variable
depth and serialised syntax remain with the applicable common match contract.
The example is not an implemented parser or prescribed regex dialect.

Publication/subscription, routing, discovery, security and other Topic-discriminating
Features reuse the same semantics. A match is a discrimination result; consuming
Features determine its consequence. Matching alone grants no access, publishes
nothing, schedules no delivery and selects no persistence provider. IU SecurityContext
is one consumer and does not own this common model. Canonical Topic renaming may
change matching consequences without changing TopicID and requires governance.

This is a logical DataObject, not an inferred Class, SecurityMask subtype,
Feature-specific wrapper, new named Topic, executable Function or universal IU
get()/test() catalogue. Existing accepted action/compartment criteria retain scope;
the IU model creates no parallel taxonomy or general-purpose policy interpreter.
