# Calliope

## Architectural content

- **Role/responsibility:** management/governance of foundational models, definitions
  and mutable datasets, including first-class Security and Assurance Nomenclature
  and authoritative review of ontology sets for Harmonia use. [U13](../../../../docs/markdown/05-information-systems-architecture/sources.md#u13),
  [canonical Calliope view](../../../../docs/markdown/05-information-systems-architecture/calliope-models-and-datasets.md).
- **Distinct submodules:** **Calliope-Models C41** supplies design/build-time
  Models, Metadata Types, Criteria Definitions, Topics, Filter Types, Filter Elements,
  core Harmonia element libraries and security/assurance definitions.
  **Calliope-DataSets C42** manages runtime mutable ValueSets, CodeSets, Structured
  Metadata and applicable governed ontology content. No common lifecycle or
  undifferentiated metadata repository is inferred.
- **Authority:** development representations support type-safe human/IDE/AI-assisted
  programming; current membership/content uses runtime authority. Models/build
  definitions establish structural access contracts; DataSets do not bootstrap them.
  Definition ownership confers neither runtime execution nor originating clinical authority.
- **Persistence/collaboration:** DataSets uses established Mneme/Mnemosyne
  responsibilities; Calliope is not a Persistence Manager. Governed workflow may
  reuse Ponos/Ergo/Praxis, without another engine or detailed management UI.
  Themis decides/enforces, Dokimasia assures and Kleio audits.
- **Standing:** U13 settles the two responsibilities, not their packaging, runtime
  ontology boundary or representation/workflow mechanisms (CDG-24/49). Existing
  pure-library dependency constraints apply to Models; U15 resolves the
  [realisation boundary](../../../../docs/markdown/05-information-systems-architecture/calliope-models-and-datasets.md#calliope-realisation).
  General converter-support
  versus activity allocation remains CDG-05; no terminology product is selected.

<a id="authorisation-nomenclature"></a>

#### Controlled authorisation nomenclature

[U12](../../../../docs/markdown/05-information-systems-architecture/sources.md#u12) establishes these **release-bounded ValueSets**:

| ValueSet | Architectural shorthand / meaning |
| :--- | :--- |
| `Application.Function.AuthorisationPoint.Names` | **Function.Name**: architecturally significant application AuthorisationPoints at which enforcement is meaningful. An AuthorisationPoint identifies a governed function; it is not itself a permission. |
| `Application.Function.AllowedAction.Names` | **Function.Scope**: the bounded set of actions applicable at AuthorisationPoints. Existing concepts include **ACCESS**, **CHANGE** and **FORWARD**; these are not asserted to be the complete final ValueSet. |
| `Information.Compartments` | Governed information compartments; an applicable dimension is expressed as **Information.Compartment**. |
| `Information.Classification` | Governed information classifications. |

`Application.Function.AuthorisationPoint.Names` SHALL be comprehensive enough
to satisfy business security requirements for the release while constrained
enough to avoid unnecessary management, development and support burden.
Complete release-specific contents remain [deferred](../../../../docs/markdown/05-information-systems-architecture/gaps.md#identity-deferred-design).

**Calliope defines/governs the nomenclature. Themis owns policy association,
resolution and enforcement.** ValueSet membership alone grants no authority
and does not establish every Cartesian combination as meaningful or permitted.

The controlled vocabularies fall within [Calliope-DataSets](466ad8f75a954c0581b5bba090443849.md);
their structural definitions/contracts belong to Calliope-Models. This allocation
does not reopen U12 or permit unrestricted runtime changes to release-bounded
content; detailed release/change rules remain deferred.

<a id="calliope-realisation"></a>

### Library dependency and runtime management

> **Calliope-Models provides development/build-time library dependencies.
> Calliope-DataSets provides runtime management and authoritative access to
> mutable governed datasets.**

The existence of DataSets does not alter Models' library/dependency semantics
and does not make Calliope a persistence manager. Repository pure-library and
zero-higher-layer-dependency constraints apply to Models; they do not restrict
all logical Calliope responsibilities to libraries. DataSets collaborates through
established Mneme/Mnemosyne access and persistence. No new static dependency or
physical allocation is inferred from that runtime collaboration.

```text
Calliope
  +-- Calliope-Models
  |     design / code / build-time model and library dependency
  `-- Calliope-DataSets
        runtime governed dataset management / authoritative content access
          ↓
        Mneme / Mnemosyne access and persistence

Concept / structural contract       → Calliope-Models
Current governed membership/content → Calliope-DataSets
```

> **Build-time representation and runtime authority are complementary, not
> competing, responsibilities.**

Strategy's library/local-evaluation statements concern Models. Calliope is not
a mandatory mediator of every runtime transaction; current governed content may
require DataSets runtime resolution. Packaging, APIs and other mechanisms remain
[deferred](../../../../docs/markdown/05-information-systems-architecture/gaps.md#calliope-contracts).

Source: `docs/markdown/05-information-systems-architecture/calliope-models-and-datasets.md` — ## Build-time knowledge and runtime authority. Standing: Candidate — adjudicated Domain05 Step-B baseline; final Solution Architecture unapproved.

> **Build-time Calliope knowledge assists software development; runtime Calliope
> authority determines validity and current governed membership/content.**

Calliope SHALL provide development-time representations of known runtime-managed
DataSets, CodeSets and ValueSets sufficient for efficient human, IDE-assisted and
AI-assisted software development. Such representations can support type safety,
code completion, documentation, static analysis and testing, with stable identity,
meaning, constraints, known build-time values and runtime-resolution contracts.

> **Development-time knowledge SHALL NOT be treated as authoritative evidence of
> current runtime membership or content.**

> **Development-time representation SHALL NOT require developers to sacrifice
> normal type-safe/code-assisted programming merely because a dataset is runtime
> mutable.**

A runtime value is not invalid merely because an earlier build did not know it.
Conversely, earlier software need not contain value-specific business behaviour
for later additions. Validation/membership uses current governed runtime authority;
the generated-code, IDE, AI-tooling and runtime access mechanisms remain deferred.

Structural contracts for accessing/managing DataSets SHALL derive from
Calliope-Models and the software build/deployment lifecycle. Runtime DataSets
provide mutable content under those contracts; they SHALL NOT bootstrap the
structural contracts required for their own access. This separates foundational
software dependency from runtime collaboration with Mneme, Mnemosyne and Ponos.
