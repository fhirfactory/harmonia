# Current-to-historical processing dependency analysis

Date: 2026-10-20. Scope: discovery against the current RAD-1.1.1 working repository. Status: analysis, not an architectural decision, implementation specification, migration instruction or disposal authority.

## Executive summary

**No: historical processing cannot be made unavailable today while retaining the existing architecture machinery's supported publication, governed-source validation and regression capabilities.** Reading the existing published RAD-1.1.0 model and comparing explicitly supplied models without baseline context are substantially more independent. Those narrower capabilities do not establish independence of the complete machinery.

The principal findings are:

1. The maintained RAD-1.1.0 publisher reconstructs the accepted publication from a historical candidate and reconciliation context. Its input loader actually opened ten processing files during this investigation. The complete governed publication exists outside processing, but the publisher does not use it as its complete source boundary.
2. Governed-source and metadata validation require historical identity-establishment copies, recovery artefacts, source-era authority snapshots and registered governance transitions. Some copies contain information already present in maintained source; their operational role is proving historical continuity, not supplying missing architectural facts.
3. The older publication chain still takes View selection, exceptions and a semantic eligibility census from processing. These are effective publication configuration and expected results, even though their directories describe past work.
4. Current tests consume actual transport specimens, saved comparator findings, complete Run-002 output/snapshot populations, selected before states and all ten files in the non-RAD 1.0.14 archive. A declared fixture manifest does not make its externally located payload independent of processing.
5. Optional historical adapters and run-local verifiers have much broader dependencies: archived executable code, entire earlier runs, local logs, native backups, temporary-workspace expectations and all-file preservation ledgers. These are distinct from prerequisites for ordinary architecture operation.

There is also an existing **release-applicability problem**, independent of making history unavailable. Root authority is `1.1.1`, previous `1.1.0`; the current published architecture is still `1.1.0`, as the governed package index and governance-only installation decision specify. Several tools select root-version publication paths or accept only exact historical releases. Default discovery currently reports a missing/ambiguous baseline. The synchronisation input loader currently stops on the changed `AGENTS.md` authority pin after opening historical recovery and governance files. Historical material being present does not make every old command applicable or successful today.

The five underlying dependency classes are **architecture reconstruction**, **identity/authority continuity**, **presentation configuration**, **regression specimens and expected results**, and **optional historical execution/recovery/preservation audits**. Section 10 reduces the detailed inventory to those classes. No cleanup plan is proposed.

Method:

- Searched maintained tools, tests, root scripts, Makefiles, schemas, JSON manifests, instructions and documentation for literal and constructed historical paths, aliases, imports, `runpy`, subprocesses and directory enumeration. Expanded exact historical-location mappings and manifest-selected paths.
- Read call sites and their conditions. A path stored inside source or a report is not automatically a file read. Conversely, a hash-only read, directory-existence requirement or manifest enumeration is an operational dependency even when it supplies no semantic content.
- Inspected historical scripts reached by maintained code and the release/replay/transport scripts identified by the current publication history. Distinguished maintained entry points from historical programs that have no maintained caller.
- Performed bounded, read-only input-loader probes with Python bytecode writing disabled and an audit hook refusing filesystem writes. These loaded and validated inputs; they did not invoke publication, candidate generation, reconciliation rendering or historical executable replay.
- Inspected actual XML populations and selected byte equivalence, manifest membership, path existence and tracking status. No original was reconstructed and no historical file was changed.

**Completeness convention:** inventory entries identify each distinct read contract and all its consumers, rather than listing one row per hash-checked snapshot. For a manifest-controlled collection, the exact population is the specified field's members resolved by the described consumer; Appendix A records the enumeration rules and counts. An asterisk in a path denotes that explicit consumer enumeration, not a proposed migration scope. Static reachability is not presented as successful execution of all branches. A full runtime trace of every possible CLI argument is outside this analysis; arbitrary explicitly supplied paths remain caller inputs.

Operational markings:

- **N**: maintained normal publication/source-validation capability, including its current blocked or release-qualified branch. It does not assert that a command succeeds under root 1.1.1.
- **T**: maintained test requirement. Tests are part of maintained assurance, separately identified from runtime authoring/publication.
- **R**: explicitly invoked maintained historical recovery/replay/report/audit capability; optional to normal architecture work.
- **H**: run-local historical program; no maintained automatic caller identified, except where a row explicitly says otherwise. Direct invocation may still be useful and may fail its historical preconditions today.
- **D**: navigation or documentary reference only; no executable content read established.

Likely-home markings use exactly the requested classifications: **AS** maintained architectural source; **GC** maintained governance/configuration; **GR** governed release; **TF** legitimate declared test/validation fixture; **FF** maintained framework functionality; **HO** historical-only material that current operation should no longer require; **SA** unresolved — requires Solution Architect adjudication. These classify information/capability, not a destination directory or authority to move the carrier. A TF finding identifies a valid testing purpose; it does not approve permanent retention of every file in its present workspace.
