# Information Architecture first-pass Change Review — RAD-1.0.10

**Review:** `2026-10-19-information-architecture-first-pass`; **author:** Codex;
**date:** 2026-10-19 (Australia/Sydney). Analysis only, before adjudication and
reconciliation. All Dispositions above are initial/default On-Hold, not issued
Solution Architect decisions. No change in this review is accepted or executed.

## Finding

The export evidences **38 existing BusinessObjects evolved into DataObjects,
explicitly specialised as Topic, renamed, documented and moved into the Application
InformationMap**. It also contains **32 genuinely new DataObject Topics**, **59
new Compositions**, **one new Aggregation**, **11 new domain Views** and one
populated existing overview. **All 1,362 baseline canonical identities survive
exactly once. No governed element is deleted.** Twelve BusinessObjects and the
four pre-existing DataObjects remain unchanged.

The existing machinery validates Exchange syntax/references and exposes raw
representation differences, but **does not correctly classify this as an IA change
set**. The key failure is correlation by Exchange identifier: the 38 evolved
resources retain `canonicalId` but have different Exchange element identifiers.
The tools consequently report missing/additional records and possible binding
reuse, rather than the preserved-instance type changes, specialisations, renames
and relocations. They also lack a Topic-aware semantic ingestion path. The
first-pass test preserves governed architectural identity successfully in the
submitted data; the current automated interpretation does not follow it fully.

## Detection method and confidence

1. Parse each complete XML, resolve property-definition references by their exact
   unique definition names, and retain native `xsi:type`, native Name,
   Documentation, relationship endpoints, organisation paths and Views separately.
2. Validate canonical claims before correlating. Each baseline `canonicalId` has
   exactly one incoming owner. All values are valid UUID32; there are no duplicate,
   malformed or multiple canonical claims. Correlate these identities first.
3. For each canonical match, compare both representation IDs and authored fields.
   For an incoming element without a canonical ID, check its Exchange ID against
   all baseline elements before calling it new. All 32 such elements have new
   Exchange IDs and no baseline canonical binding; no name-based matching is used.
4. Compare explicit semantic relationships by representation identity, native
   type, source, target, direction and specialisation. Trace incoming containment
   only through actual Composition records. Do not turn folders, prose references
   or visual nesting into relationships.
5. Run existing read-only diagnostics against both the publication and the exact
   no-edit transport control. Use the control to distinguish pre-existing transport
   findings from this modelling pass, without changing comparator rules.

A short-lived analysis script and JSON indexes were written under `/tmp` only.
They inspect evidence; they do not implement or amend repository ingestion tooling,
allocate identities, repair names or create reconciliation instructions. Exact IDs,
source lines, counts, findings and candidate meanings are retained in this report
so that temporary files are not required to understand its conclusions.

**High confidence:** canonical continuity, actual native retyping, explicit Topic
specialisation, raw renames, navigation moves, Documentation changes, new records,
explicit relationship types/endpoints and View membership. **Unresolved:** accepted
architectural scope of the proposals, future representation rebinding, detailed
meaning of certain new information and relationship assertions, and governed
metadata derivation after acceptance. GUI action sequence and intent beyond the
submitted evidence remain unknown.
