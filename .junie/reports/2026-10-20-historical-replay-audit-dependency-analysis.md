# Historical replay and audit dependency analysis — Dependency Class 5

Date: 2026-10-20. Status: analysis for the Solution Architect. This report supplies no architectural acceptance, retention/disposal decision, reconstruction authority or implementation instruction.

## 1. Executive summary

**No examined capability establishes an intrinsic need to preserve a complete historical processing run as a complete run for normal architecture operation or recovery of current maintained state.** This is not a finding that existing machinery is independent of processing. Current loaders, tests and optional audits still require particular historical files, and some deliberately quantify over large historical populations.

There are legitimate additional capabilities beyond architecture provenance:

1. **Run-002 algorithm/output diagnosis and bounded candidate replay.** Archived code, specimens, expected outputs and selected correction states permit investigation of effective containment, independently generated workspace navigation, contained-leaf self-folders and protected Relations/Views. Actual failure logs retain observations that a final passing candidate cannot supply. The existing isolated replay restores archived code, but does not reproduce the complete original execution or all run files.
2. **Inspection of observed Archi transport.** Actual input/export pairs and attributable execution/profile records support empirical analysis of property loss, folder identity/order and complete View preservation. An architecture transition package does not prove what an independent tool exported. Rechecking retained XML is different from rerunning Archi or authenticating an earlier invocation.
3. **Specific historical integrity audits.** Exact ten-file non-RAD relocation, correction boundaries and historical review/result overlays answer identifiable earlier-execution questions. They are historical audit, not evidence of current architectural authorisation. Whether the broadest all-file assurances deserve continuing support remains an explicit adjudication matter.
4. **Intermediate identity evidence.** The original IA allocation-before-name-completion source is a distinct intermediate boundary. Its exact bytes are not supplied by the governed transition endpoints or the inspected normal-source-path Git history. The snapshot itself is tracked in Git. Its stronger intermediate guarantee remains unresolved; its existence must not be dismissed or expanded into a requirement for the containing run.

**No additional fourth architecture-provenance component is justified.** For an authorised transition, exact changed-file before/after content and an attributable, complete `change-review.md`, interpreted with the identified governed baseline, answer the architectural question. Old command logs, candidate regeneration and hash ledgers answer different questions. Existing historical packages were not constructed or assumed complete here.

The strongest replay specimen, Run-002, is **not a turnkey self-contained replay package**. The reproducer reads 28 frozen files from outside its own run; today's root release bytes already fail one of those pins, and one operand is an untracked native backup. It uses the host Python/lxml environment. Its assertions reproduce five outputs exactly and selected rebinding fields, not the complete machinery execution. No historical executable was run or repaired for this analysis.

The final reduction is: no new Class-5-only operational/recovery information requirement; bounded valuable diagnostic/replay observations; architecture-provenance roles superseded in principle by the approved contract; behavioural roles belonging to deliberate fixtures; execution-only material with no identified durable purpose; and specific unresolved assurance/authority questions. These categories overlap within files and confer no disposal authority.
