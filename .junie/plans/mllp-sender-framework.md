# Requirements

### Overview & Goals
The Harmonia platform requires a dedicated, resilient, and enterprise-grade **MLLP Sender Framework** (`pylai-mllp-out`) within the **Pylai Gateway Tier**. While Harmonia currently provides robust inbound MLLP ingestion (`pylai-mllp-in`), healthcare interoperability demands bidirectional integration where clinical events (e.g., ADT patient updates, MFN master file notifications, ORU observations, MDM documents) processed by the Ponos/Praxis workflow engine or triggered by external REST clients can be transmitted reliably over standard Minimal Lower Layer Protocol (MLLP / TCP) to remote clinical systems (e.g., Hospital Information Systems, Electronic Medical Records, Laboratory Information Systems, PACS, and Regional Health Registries).

The primary goals are:
1. Provide a high-throughput, non-blocking MLLP egress gateway (`pylai-mllp-out`) powered by Apache Camel and Jakarta EE 10 / WildFly.
2. Support multi-instance egress architecture with dedicated, independent **Petasos** messaging queues (Artemis JMS) per target endpoint/instance (e.g., `petasos.queue.mllp.outbound.<endpoint-id>`), preventing head-of-line blocking and providing complete fault isolation across remote destinations.
3. Support dual ingress modes: asynchronous consumption of outbound tasks from dedicated **Petasos** messaging queues and synchronous dispatch via **JAX-RS REST** endpoints.
4. Support dynamic destination resolution via a configurable **Destination Target Registry** mapped against canonical `Topic` metadata (destination, facility, message type) as well as dedicated instance-to-endpoint pinning.
5. Enforce strict **HL7 v2 Acknowledgement (ACK/NACK)** validation (matching MSA-2 control IDs against MSH-10, handling `AA`/`CA`, `AE`/`CE`, `AR`/`CR`, and timeouts).
6. Maintain comprehensive **FHIR R5 Resource Lifecycle & Provenance** by generating/updating `Communication`, `Task` (`Pragma`), and `Provenance` resources in the **Mneme** Infinispan in-memory cache grid.
7. Provide resilient error handling, exponential backoff retries, and dead-letter queue (DLQ) support for transient network failures per endpoint instance.

### Scope
#### In Scope
- **`pylai-mllp-out` Module**: WildFly Jakarta EE 10 WAR submodule under `pylai` supporting multi-instance deployments, exposing REST endpoints (default port `8087`), and managing Camel MLLP producer endpoints.
- **Dedicated Independent Petasos Queues per Endpoint**: Independent Artemis JMS task queues per target endpoint/instance (e.g., `petasos.queue.mllp.outbound.<endpoint-id>`), ensuring independent backpressure, queue monitoring, and failure domain isolation.
- **`pylai-mllp-base` Extensions**: Shared outbound models (`OutboundMllpRequest`, `OutboundMllpResponse`), destination configuration (`MllpDestinationConfig`), and `MllpDestinationRegistry`.
- **Dynamic Destination Routing & Instance Pinning**: Resolution of target remote host, port, timeout, charset, and TLS parameters based on `Topic` / request metadata, with support for endpoint-pinned instance profiles.
- **Camel MLLP Dispatch Engine**: Apache Camel MLLP producer routes (`mllp://...`) with connection pooling, framing (`<VT>...<FS><CR>`), and keep-alive handling.
- **HL7 v2 ACK/NACK Evaluation**: Full parsing and validation of commit and application acknowledgements.
- **State & Audit Lifecycle**: Generation and caching of FHIR `Communication`, `Task` (`Pragma`), and `Provenance` resources in Mneme cache via Hot Rod client, plus Petasos completion event publishing.
- **CLI & Diagnostic Tooling**: Outbound test command extensions in `pylai-mllp-cli` and containerization in `docker-compose.yml` demonstrating multi-instance egress routing.

#### Out of Scope
- Direct modification of third-party external MLLP listener implementations.
- Non-MLLP egress protocols (e.g., direct FHIR REST egress is handled via BEFE/Hestia).
- Custom proprietary non-HL7 framing protocols.

### User Stories
- **As an Integration Engineer**, I want Harmonia to automatically transmit outbound HL7 v2 messages generated by workflow task sequences to external EMRs over MLLP so that external clinical systems remain synchronized.
- **As a System Architect**, I want each outbound endpoint to have an independent Petasos queue and dedicated sender instance so that an outage or slow response from one destination system does not stall or delay message delivery to other destination systems.
- **As a Clinical System Administrator**, I want outbound MLLP transmissions to validate HL7 ACKs and record audit trails (`Communication`, `Provenance`) so that message delivery can be verified and audited.
- **As an Operations Specialist**, I want transient network interruptions to be retried automatically with backoff and persistent failures routed to an endpoint-specific dead-letter queue so that messages are not silently dropped.
- **As a Test Engineer**, I want to trigger outbound MLLP transmissions via REST endpoints and CLI commands to validate connectivity with external receiving endpoints during onboarding.

### Functional Requirements
- **FR-1 (Independent Petasos Queue Ingestion per Endpoint/Instance)**: Consume outbound dispatch tasks from dedicated Petasos Artemis queues partitioned by target endpoint or sender instance ID (e.g., `petasos.queue.mllp.outbound.<endpoint-id>`), guaranteeing queue-level isolation, independent concurrency control, and failure containment across endpoints.
- **FR-2 (REST Ingress API)**: Provide JAX-RS REST endpoints (`POST /api/mllp/outbound/send`, `/api/mllp/outbound/adt/send`, `/api/mllp/outbound/mfn/send`) accepting HL7 payloads or structured task requests for immediate dispatch.
- **FR-3 (Dynamic Destination Resolution & Endpoint Pinning)**: Resolve remote IP/hostname, TCP port, timeout (connect/read), charset, and autoAck parameters via `MllpDestinationRegistry` using `Topic.destination` or task metadata, supporting both dedicated pinned instances and dynamically routed multi-destination instances.
- **FR-4 (MLLP Framing & Transport)**: Encapsulate HL7 v2 message strings within standard MLLP envelope (`0x0B` start block, payload, `0x1C` end block, `0x0D` carriage return) and transmit over TCP socket.
- **FR-5 (ACK Parsing & Validation)**: Extract MSA segment from returned ACK; verify MSA-2 matches outbound MSH-10 message control ID; evaluate acknowledgement code (`AA`/`CA` -> success; `AE`/`CE`/`AR`/`CR` -> failure).
- **FR-6 (FHIR Resource & State Tracking)**:
  - Create/update FHIR `Communication` resource representing the transmission with outbound payload and returned ACK.
  - Update `Pragma` task status (`IN_PROGRESS` -> `COMPLETED` / `FAILED`) with execution timestamps and checkpoint notes.
  - Create FHIR `Provenance` resource recording the activity, target entity, and timestamp.
  - Persist all resources into Mneme Infinispan cache grid via Hot Rod client.
- **FR-7 (Petasos Completion Events)**: Publish `ErgonEvent` to Petasos broker signaling completion or failure of the outbound task.
- **FR-8 (Error Handling & Retry Policy)**: Provide configurable retries with exponential backoff for socket timeouts, connection refused, and transient network errors; forward unrecoverable messages to an endpoint-specific DLQ.

### Non-Functional Requirements
- **High Availability**: Stateless WildFly deployment capable of running multi-instance active-active behind a load balancer.
- **Performance**: Sub-50ms dispatch-to-ACK turnaround for local network endpoints with non-blocking I/O.
- **Fault Tolerance**: Automatic reconnection and timeout management without thread starvation.
- **Security & Conformance**: Strict HL7 v2 standard adherence and ISO-8859-1 / UTF-8 charset compliance.

# Technical Design

### Current Implementation
Harmonia currently contains:
- `pylai-mllp-in`: Inbound MLLP gateway listening on TCP port `2575` (HTTP `8084`) using Apache Camel `mllp://` server component. Ingests HL7 messages, creates synthetic `Task` and `Communication` FHIR resources in Mneme cache, and sends `ErgonEvent` to Petasos Artemis queue.
- `pylai-mllp-base`: Shared library containing `CommunicationService`, `TaskService`, `ProvenanceService`, `TaskEventProducerService`, `HotRodClientProducer`, and `FhirConfig`.
- `pylai-mllp-cli`: Diagnostic CLI tool with `MllpClient` implementing socket-level MLLP transmission for synthetic test messages.
- `energeia/ponos`: Asynchronous workflow engine consuming `Pragma` tasks and executing `Erga` activity pipelines.

### Key Decisions
1. **Dedicated Gateway Module (`pylai-mllp-out`) & Multi-Instance Egress**:
   - *Decision*: Implement a dedicated WildFly WAR module `pylai-mllp-out` in the Pylai tier that supports running multiple sender instances, each configured with an instance ID and dedicated target endpoint binding.
   - *Rationale*: Maintains clean 5-tier separation of concerns, decouples network-facing socket management from the Ponos workflow engine, and allows independent scaling and failure isolation across different remote clinical endpoints.
2. **Independent Petasos Queues per Target Endpoint / Instance**:
   - *Decision*: Assign an independent Artemis JMS queue per target endpoint/sender instance (e.g., `petasos.queue.mllp.outbound.<endpoint-id>`). The upstream workflow engine (Ponos) routes outbound tasks directly to the destination endpoint's specific queue, and each `pylai-mllp-out` instance consumes from its assigned queue.
   - *Rationale*: Prevents head-of-line blocking (e.g., a slow or down HIS cannot delay messages destined for LIS or PACS), enables fine-grained queue monitoring and throttling, and provides complete fault domain isolation.
3. **Dual Ingress Architecture (Petasos JMS + JAX-RS REST)**:
   - *Decision*: Support both asynchronous message-driven execution via Petasos Artemis queues and synchronous/on-demand execution via REST.
   - *Rationale*: Workflow tasks triggered by Ponos flow seamlessly through Petasos queues, while external test suites, CLI tools, and synchronous integration services can trigger transmissions directly via REST.
4. **Dynamic Target Destination Registry & Pinned Endpoint Profiles**:
   - *Decision*: Implement `MllpDestinationRegistry` backed by structured configuration and `Topic` metadata matching, allowing sender instances to operate either as pinned single-endpoint gateways or dynamic multi-endpoint routers.
   - *Rationale*: Egress systems must dispatch messages to diverse downstream systems (HIS, LIS, RIS, external EMRs) with varying hostnames, ports, timeouts, and character encodings.
5. **Full FHIR & Pragma State Synchronization**:
   - *Decision*: Synchronize every outbound dispatch with FHIR `Communication`, `Task` (`Pragma`), and `Provenance` resources committed to Mneme cache.
   - *Rationale*: Ensures end-to-end clinical traceability, audit compliance, and consistency across Iris presentation tier and Mnemosyne relational storage.

### Proposed Changes
#### 1. `pylai-mllp-base` (Shared Gateway Foundation)
- **`MllpDestinationConfig.java`**: POJO encapsulating `destinationId`, `name`, `host`, `port`, `connectTimeoutMs`, `readTimeoutMs`, `charset`, `keepAlive`, `autoAck`, and `enabled`.
- **`MllpDestinationRegistry.java`**: Application-scoped registry managing active destination endpoints with lookup by destination ID and `Topic` metadata.
- **`OutboundMllpRequest.java` / `OutboundMllpResponse.java`**: Canonical transfer models for outbound payloads, control IDs, ACK codes, response bodies, and latency metrics.
- **`OutboundResourceBuilder.java`**: Factory for creating outbound FHIR `Communication` and `Provenance` resources.

#### 2. `pylai-mllp-out` (New WildFly Jakarta EE 10 WAR Submodule)
- **`pom.xml`**: Submodule POM with `pylai-mllp-base`, `calliope`, `camel-mllp`, `camel-cdi`, `hapi-hl7v2`, `infinispan-client-hotrod`, and `artemis-jms-client`.
- **`CamelContextManager.java`**: CDI bean managing lifecycle of the outbound Camel context and routes.
- **`OutboundMllpRouteBuilder.java`**: Camel route builder defining `direct:mllp-outbound-send` -> dynamic `mllp://host:port` endpoints with error handling and retry policies.
- **`OutboundMllpProcessor.java`**: Exchange processor that parses the outbound message, validates MSH headers, resolves destination, and dispatches via Camel MLLP.
- **`Hl7AckProcessor.java`**: Processor for parsing HL7 ACK segments (MSHA/MSA), checking ACK codes (`AA`/`CA` vs `AE`/`AR`), and matching control IDs.
- **`OutboundTaskQueueConsumer.java`**: Petasos Artemis consumer listening to the dedicated instance queue (e.g., `petasos.queue.mllp.outbound.<endpoint-id>` or `task.outbound.queue.<endpoint-id>`) to drive asynchronous workflow dispatch.
- **`OutboundMllpResource.java`**: JAX-RS REST resource providing `/api/mllp/outbound/send`, `/api/mllp/outbound/destinations`, `/api/mllp/outbound/health`.
- **`MllpOutboundConfig.java`**: CDI configuration provider reading `MLLP_OUTBOUND_INSTANCE_ID`, `MLLP_OUTBOUND_TARGET_ENDPOINT_ID`, `MLLP_OUTBOUND_QUEUE_PREFIX`, and broker settings to compute dedicated queue names.

#### 3. `pylai-mllp-cli` Extensions
- Add `send` / `dispatch` command options to test outbound transmission to configured `pylai-mllp-out` endpoints or direct remote targets.

### Risks & Mitigations
- **Remote Host Unreachable / Socket Timeouts**: Mitigated by non-blocking socket timeouts, exponential backoff retries, circuit breaking, and dead-letter queue routing.
- **Mismatched Message Control IDs in ACKs**: Mitigated by strict MSA-2 validation against original MSH-10 control IDs with detailed error logging in the generated `Communication` resource.
- **Connection Leaks on High Concurrency**: Mitigated by Apache Camel MLLP connection pooling and managed socket lifecycle in `CamelContextManager`.

# Testing

### Validation Approach
The validation strategy employs multi-tiered testing comprising unit tests, Camel route integration tests with mock MLLP endpoints, Petasos queue integration tests, and end-to-end verification.

### Key Scenarios
1. **Synchronous REST Outbound Dispatch**:
   - Send valid HL7 ADT A01 message via `POST /api/mllp/outbound/send` to a configured destination.
   - Verify MLLP client frames message, receives `AA` ACK, records `Communication` with status `completed`, updates `Task` (`Pragma`), and returns HTTP 200 with `OutboundMllpResponse`.
2. **Asynchronous Petasos Queue Workflow Dispatch with Dedicated Queues**:
   - Publish an outbound task `ErgonEvent` to target-specific queue `petasos.queue.mllp.outbound.his`.
   - Verify the HIS sender instance `OutboundTaskQueueConsumer` picks up the task from its dedicated queue, dispatches via Camel MLLP route, parses ACK, updates Mneme cache, and emits completion event to Petasos without touching or interfering with other endpoint queues (e.g. `petasos.queue.mllp.outbound.lis`).
3. **Multi-Instance Failure Domain Isolation**:
   - Simulate an outage on the HIS remote receiver while LIS remains active.
   - Verify `petasos.queue.mllp.outbound.his` enters retry/DLQ backoff while `petasos.queue.mllp.outbound.lis` continues processing and dispatching messages at full speed without obstruction.
4. **Dynamic Destination Resolution & Endpoint Pinning**:
   - Dispatch message targeting a specific facility code or destination ID registered in `MllpDestinationRegistry`.
   - Verify route connects to the dynamically resolved host and port.
5. **HL7 Application Reject / NACK Handling**:
   - Send message to mock server returning an `AE` or `AR` NACK.
   - Verify `Hl7AckProcessor` detects rejection, marks `Communication` as `not-done`, marks `Pragma` as `FAILED`, and records diagnostic error details.
6. **Connection Failure & Retry Backoff**:
   - Dispatch to an unreachable host/port.
   - Verify configured retries execute with backoff, fail gracefully, and route failed task to the instance-specific dead-letter queue without blocking other transmissions.

### Edge Cases
- **Malformed ACK Payload**: Mock receiver returns non-HL7 garbled response; system flags format error and preserves raw response in `Communication` resource.
- **Read Timeout During ACK Waiting**: Socket timeout triggers cleanly, releases connection, and transitions task to retry/timeout state.
- **Special Characters and UTF-8 Payloads**: Messages containing multi-byte characters are encoded and framed properly without truncation.

### Test Changes
- `pylai-mllp-base`:
  - `MllpDestinationRegistryTest.java` (test destination registration, lookup, fallback, and validation).
  - `OutboundMllpResponseTest.java` (test response factory methods and ACK parsing).
- `pylai-mllp-out`:
  - `OutboundMllpRouteTest.java` (Camel test kit verifying MLLP framing, route execution, and error handling).
  - `Hl7AckProcessorTest.java` (test parsing `AA`, `AE`, `AR`, `CA`, `CE`, `CR`, and missing MSA segments).

  - `OutboundTaskQueueConsumerTest.java` (test JMS queue message consumption and pipeline forwarding).
  - `OutboundMllpResourceTest.java` (REST API endpoint testing).
